===============================================================================
        AI-AGENT-SANDBOX — объяснение репозитория (простыми словами)
===============================================================================

ЧТО ЭТО ТАКОЕ?
-------------------------------------------------------------------------------
Это "песочница" — изолированный Docker-контейнер, внутри которого можно
безопасно запускать ИИ-агентов (opencode, Claude Code и т.п.), чтобы они
писали код в твоём проекте.

Зачем? ИИ-агент выполняет команды на твоём компьютере. Если дать ему доступ
напрямую — он теоретически может:
  - залезть в твою локальную сеть (роутер, NAS, другие компьютеры),
  - прочитать cloud metadata (169.254.169.254) и украсть учётные данные,
  - установить что-то вредоносное,
  - сломать систему.

Здесь агент заперт в "клетке":
  1. У него НЕТ прямого интернета. Весь трафик идёт через прокси.
  2. ИНТЕРНЕТ РАЗРЕШЁН ЦЕЛИКОМ — никаких белых списков сайтов.
  3. ЗАПРЕЩЁН доступ только к ЛОКАЛЬНЫМ подсетям:
     - частные сети: 10.x.x.x, 172.16-31.x.x, 192.168.x.x (там роутер,
       принтер, NAS, другие контейнеры Docker);
     - loopback: 127.x.x.x, ::1 (сам прокси и локальные сервисы);
     - link-local: 169.254.x.x (включая 169.254.169.254 — cloud metadata,
       где AWS/GCP/Yandex Cloud раздают секретные токены!);
     - плюс прочие служебные диапазоны и IPv6-аналоги (fc00::/7, fe80::/10);
     - плюс "локально выглядящие" имена: localhost, *.local, *.lan,
       *.internal, *.home, *.corp.
  4. У агента нет прав root, он работает под твоим пользователем.
  5. Жёсткие лимиты: максимум 4 ГБ памяти, 2 ядра CPU, 512 процессов.

Итог: агент может качать пакеты, ходить на GitHub и к любым API в интернете,
но не может достучаться до твоей локальной сети и соседних контейнеров.


КАК ЭТО УСТРОЕНО (схема)
-------------------------------------------------------------------------------

    ┌────────────────────────── ТВОЙ КОМПЬЮТЕР ──────────────────────────┐
    │                                                                     │
    │   Твой проект (например ~/Projects/my-app)                          │
    │        │                                                            │
    │        │  монтируется как папка /workspace                          │
    │        ▼                                                            │
    │   ┌─────────────────────┐         ┌──────────────────────┐          │
    │   │   КОНТЕЙЕР "agent"  │ HTTP(S) │  КОНТЕЙЕР "proxy"    │          │
    │   │                     ├────────►│  (Squid, порт 3128)  │          │
    │   │  здесь сидит        │  через  │                      ├──► ИНТЕРНЕТ
    │   │  ИИ-агент           │  proxy  │  блокирует запросы   │   (весь)
    │   │                     │         │  в локальные сети    │
    │   │  интернет: НЕТ      │         │                      │
    │   │  (сеть internal)    │         │  ЛОКАЛЬНЫЕ СЕТИ: 403 │
    │   └─────────────────────┘         └──────────────────────┘          │
    └─────────────────────────────────────────────────────────────────────┘


ФАЙЛЫ В РЕПОЗИТОРИИ (что каждый делает)
-------------------------------------------------------------------------------

docker-compose.yml
    Главный файл. Описывает два контейнера:
      * proxy  — прокси-сервер Squid (привратник интернета);
      * agent  — сама песочница, где работает ИИ-агент.
    Про агент здесь же задана защита:
      - HTTP_PROXY=http://proxy:3128  → весь трафик принудительно через прокси;
      - dns: 192.0.2.1               → фиктивный DNS: агент сам ничего не
                                        резолвит, домены резолвит прокси
                                        (заодно нет DNS-туннелей мимо прокси);
      - cap_drop: ALL + no-new-privileges → никаких привилегий root;
      - mem_limit: 4g, cpus: 2.0, pids_limit: 512 → чтобы агент не съел
                                        всю память/процессор и не устроил
                                        fork-бомбу;
      - user: твой UID:GID           → файлы в проекте создаются от твоего
                                        имени, а не от root;
      - volumes: текущая папка → /workspace (агент работает с твоим
                                        проектом), том agent-home → /home/agent
                                        (настройки и кэш сохраняются между
                                        запусками),
                                        папки agent-data и agent-config на
                                        хосте → сессии, история и auth-токены
                                        opencode + его конфиг (переживают всё,
                                        лежат у тебя на виду).


СОХРАНЕНИЕ СЕССИЙ OPENCODE
-------------------------------------------------------------------------------
Сессии и авторизация opencode хранятся НЕ в контейнере, а на хосте:
      agent-data/    → /home/agent/.local/share/opencode
                       (сессии, история чатов, auth.json - токены провайдеров)
      agent-config/  → /home/agent/.config/opencode
                       (твой opencode.json - настройки агента)
Папки создаются автоматически при первом запуске через sandbox-run.sh
(от твоего пользователя). agent-data/ в .gitignore - там секретные токены!
Контейнер можно удалять/пересобирать сколько угодно - сессии остаются.

    Сети:
      - "egress"  — есть выход в интернет (здесь живёт только прокси);
      - "sandbox" — internal (БЕЗ выхода в интернет, здесь живёт агент).

Dockerfile
    "Рецепт" образа для контейнера agent:
      - база: debian:trixie-slim (легковесный Debian);
      - ставится минимум инструментов: git, curl, jq, python3, ripgrep,
        nano, less, procps;
      - создаётся обычный пользователь "agent" (не root!) с UID/GID,
        совпадающим с твоим пользователем на хосте.

sandbox-run.sh
    Скрипт-запускалка. Упрощает жизнь: не нужно помнить команды docker.
    Делает:
      1. Запоминает твой UID/GID и текущую папку;
      2. Поднимает прокси (docker compose up -d proxy);
      3. Собирает образ агента (docker compose build agent);
      4. Запускает агента с переданной командой (по умолчанию — bash).
    Использование (из папки любого проекта):
        /path/to/ai-agent-sandbox/sandbox-run.sh            → откроется bash
        /path/to/ai-agent-sandbox/sandbox-run.sh opencode   → запустится opencode

squid/squid.conf
    Конфиг прокси — правила "пропускать/не пропускать". Логика простая:
        ЗАПРЕЩЕНО: локальные подсети (IPv4 + IPv6)
        ЗАПРЕЩЕНО: имена localhost, *.local, *.internal, *.lan, *.home,
                   *.corp, *.localdomain
        ЗАПРЕЩЕНО: CONNECT-туннели на не-HTTPS порты (только 443)
        ВСЁ ОСТАЛЬНОЕ: разрешено
    Блокируемые диапазоны:
      IPv4: 0.0.0.0/8, 10.0.0.0/8, 100.64.0.0/10 (CGNAT), 127.0.0.0/8,
            169.254.0.0/16 (link-local + cloud metadata!),
            172.16.0.0/12 (частные + сети Docker), 192.168.0.0/16,
            192.0.0.0/24, TEST-NET (192.0.2.0/24, 198.51.100.0/24,
            203.0.113.0/24), 198.18.0.0/15, 224.0.0.0/4, 240.0.0.0/4
      IPv6: ::1/128 (loopback), fc00::/7 (частные), fe80::/10 (link-local)
    Важно: прокси сам резолвит имена хостов и проверяет, куда они ведут.
    Поэтому хитрость "под_fake_домен.ру указывает на 192.168.1.1" не пройдёт —
    запрос всё равно будет заблокирован по IP назначения.
    Кэширование отключено (cache deny all).

sandbox.env.example
    Шаблон файла с API-ключами:
        ANTHROPIC_API_KEY=...
        OPENAI_API_KEY=...
        GEMINI_API_KEY=...
    Как пользоваться: скопируй его в файл с именем "sandbox.env"
    и впиши туда свои ключи. Контейнер agent автоматически получит их
    как переменные окружения.

sandbox.env
    Твой РЕАЛЬНЫЙ файл с ключами (секретный). В git НЕ попадает —
    он указан в .gitignore.

.gitignore
    Указывает git'у не коммитить sandbox.env (там секреты).

.sandbox.env.swp
    ⚠ МУСОР: временный файл редактора Vim (swap-файл от правки
    sandbox.env). Остался, если vim закрылся аварийно или ещё открыт
    в другой сессии. Он может содержать твои ключи! Рекомендуется:
      1) убедиться, что vim нигде не открыт с этим файлом;
      2) удалить: rm .sandbox.env.swp
      3) добавить в .gitignore строку "*.swp"


ПОРЯДОК РАБОТЫ (как этим пользоваться)
-------------------------------------------------------------------------------
1. Разовая настройка:
      cp sandbox.env.example sandbox.env
      nano sandbox.env          # вписать свои API-ключи

2. Запуск из папки любого проекта:
      cd ~/Projects/my-app
      /home/anton/Projects/Personal/ai-agent-sandbox/sandbox-run.sh

3. Ты оказываешься в bash внутри контейнера, прямо в папке со своим
   проектом (/workspace). Здесь запускаешь ИИ-агента:
      opencode
   Агент работает, качает пакеты (npm/pip), ходит на GitHub и к любым
   API в интернете — всё через прокси. Попытки лезть в локальные сети
   отклоняются с ошибкой 403.

4. Выход — exit. Контейнер удаляется (--rm), твой проект на хосте не
   трогается, ключи и кэш остаются (том agent-home).

ЧАСТЫЕ ВОПРОСЫ
-------------------------------------------------------------------------------
В: Агенту нужен не-HTTPS порт (например SSH на 22 или свой сервис на 8080)?
О: В squid/squid.conf правило "acl SSL_ports port 443" ограничивает
   CONNECT-туннели только портом 443. Добавь нужный порт:
       acl SSL_ports port 443
       acl SSL_ports port 22
   и перезапусти: docker compose restart proxy
   (HTTP на порту 8080 и так работает — без CONNECT, обычным проксированием.)

В: Как посмотреть логи прокси (что агент пытался открыть)?
О: docker logs sandbox-proxy
   (видно каждый запрос и DENIED/ALLOWED — удобно для отладки)

В: Почему нельзя просто дать агенту интернет без прокси?
О: Сеть "sandbox" помечена internal: контейнер физически не имеет
   маршрута в интернет. Прокси — единственная "дверь", и она проверяет
   каждый запрос. Так защита не зависит от того, насколько умён/глуп агент.

В: Файлы в проекте создаются от root?
О: Нет. Скрипт передаёт твой UID/GID внутрь контейнера, поэтому все
   созданные агентом файлы принадлежат тебе.

В: Что если я добавлю ключ в sandbox.env — он утечёт в git?
О: Нет, файл в .gitignore. Но не забудь удалить .sandbox.env.swp
   (см. выше) и не копируй ключи в другие файлы.


КОРОТКО: ЗАЧЕМ ВСЁ ЭТО
-------------------------------------------------------------------------------
Это способ доверить ИИ-агенту работу над кодом, не давая ему полную
свободу на твоём компьютере: интернет есть, но локальная сеть,
cloud metadata и системные сервисы — за стеной. Всё под контролем
и с лимитами.
